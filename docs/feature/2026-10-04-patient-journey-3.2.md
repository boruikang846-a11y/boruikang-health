# 博瑞康门诊与出院全旅程服务开发方案 V1.2

2026-10-04。根据用户最新明确目标调整：系统围绕患者在医院门诊或住院出院的一次服务旅程，完成院前、院中、院后、复诊与结果确认。沿用此前合并的“诊后主动干预”，作为旅程中的业务执行中心。

## 产品主线与本次修改

新增主入口“患者全旅程服务”，保留扫码接入、诊前筛查、诊后主动干预、角色工作台和复盘。一个患者主档下可有多个就诊事件，每个事件有独立旅程、节点证据及操作者。阶段不是患者唯一状态，接入授权、联系、预约、医疗计划与旅程状态分别保存。

门诊路径：接入与服务交接 → 咨询及预约协助 → 实际到院核验 → 院内检查与流程协助 → 门诊结束及医嘱核对 → 诊后计划审核 → 随访执行与反馈 → 复诊结果及服务结案。

住院出院路径：接入与服务交接 → 住院服务及问题协调 → 出院小结与医嘱核对 → 出院准备及管家交接 → 出院后计划审核 → 居家随访与反馈 → 复诊结果及服务结案。

临床医生把关医疗依据、计划与临床反馈；护士/健康管家负责服务协助、联系、收集反馈、结果核验与服务结案。AI提供辅助草稿，服务闭环不依赖模型自动作决定。

## 可操作原型与边界

本次原型可建立两类旅程，按患者及就诊事件防重复登记；记录每个阶段的人工核验依据、操作者、录入时间，关联现有报告、计划、随访和预约页面。

完成节点须按顺序，旧节点重复提交拒绝；未核验/未授权/未交接时不能建立旅程，撤回服务授权后暂停后续节点。当前责任医生才能确认已阅门诊或出院报告及当前获批计划。随访节点关联已完成且责任医生审核的任务，已关联另一旅程的任务不能重复用于新旅程；计划版本变更后不沿用旧计划依据。门诊首次到院关联已到院预约，不以预约成功代替实际到院。

结案前无未结咨询和异常；复诊完成须关联已到院记录，首次门诊到院不能再算一次复诊。无需本轮复诊由责任医生说明依据，管家再确认结果；患者退出保留退出证据，不算正常复诊完成。结案属于本次服务闭环，不表示患者已经治愈或结束所有长期计划。

以下仍为原型限制：数据保存在页面内存；人工证据没有接入HIS核验；现有个体计划是患者级，旅程只记录其版本；既有随访任务通过人工选取关联，不能证明已由该就诊医嘱自动生成。发生计划版本变化时原型阻断继续，不提供完整的重审与替代旅程工作流。真实多事件计划实例化、数据库并发及消息执行另行开发。

## 逐节点开发与验收

| 节点 | 输入与负责人 | 完成证据及下一步 | 必须处理的未闭环情况 |
|---|---|---|---|
| 接入 | 患者/代理关系、服务用途授权；接入人员 | 身份核验、团队与管家接收 | 身份冲突、拒绝、未确认交接 |
| 院前咨询 | 服务需求、有效院内知识；当班管家 | 回复证据、问题解决或临床转接、预约需求 | 无依据回答、无人接单、待补充 |
| 预约及到院 | 预约事件、就诊事件；协调员 | 分开保存预约状态、实际到院状态及来源 | 数据未知待核验，不能自动认定爽约 |
| 院内服务 | 当前就医节点；护士/院内协调员 | 检查指引、准备说明、流程困难处理结果 | 动态号源或费用不承诺未核实结果 |
| 门诊结束 | 门诊病历、原医嘱版本；责任医生 | 就诊结束事件、后续服务依据 | 资料不完整待补齐，不猜医嘱 |
| 出院准备 | 出院小结、医嘱、主管团队；医生与护士 | 患者/代理理解核实、管家接收、后续安排 | 出院事件未确认、未完成交接 |
| 计划发布 | 生效模板及本次事件；临床审核+运营确认 | 事件绑定的不可变计划版本、多节点任务 | 驳回、重复事件、医嘱变更替代 |
| 随访反馈 | 授权、计划版本、任务时窗；管家 | 联系尝试、反馈原文、实际结果分别存储 | 未接通、无反馈、发送失败进入跟进队列 |
| 异常 | 原始反馈与关联计划；管家→临床团队 | 接单、处理、患者获得结果或有效交接 | 已通知不结案；超时备用队列 |
| 复诊 | 医嘱要求或明确需求；协调员 | 预约、取消、实际到院、诊疗结果分别核验 | 失约须有证据；患者退出停止对应提醒 |
| 结果确认 | 相关服务事项；管家/责任医生 | 结果、体验反馈、下一轮需求、服务结案 | 未结异常、投诉、未交接事项独立追踪 |

满意度记录全部邀请、未回应、拒绝及低分；长期陪伴按患者意愿和有效计划延续，不能以转介绍或消费转化作为服务结案必要条件。

## 数据、契约与工程实施

复用现有Java业务主服务与React前端；部署仍由boruikang-workflows维护。患者主档是统一入口，增加就诊事件、旅程实例、节点实例、节点结果、报告/医嘱快照、计划版本、任务关联、预约/到院证据、交接单和独立异常工单。旅程绑定事件及组织，历史不覆盖。

正式模型与约束：

- journey：患者、医院、来源系统、事件ID、路径版本、当前阶段、服务主责、状态。
- journey_step：旅程、步骤ID、执行资质、负责人、时间窗、状态、version、前置条件。
- journey_result：发生时间、录入时间、操作者、来源、证据引用、结果类型、原状态/新状态。
- encounter/clinical_order：源事件唯一、原医嘱不可变版本及报告引用。
- followup_plan/task：绑定本次事件、临床依据、模板版本和计划版本；步骤幂等。
- handoff：交出、接收、未解决事项、下一步、截止时间；接收前保留原责任。

正式接口依项目POST专用DTO及snake_case约定定义：创建旅程、查询清单/详情、提交节点结果、交接确认、暂停/恢复/退出、关联计划、关联预约及对账。各变更携带request_id与version，服务端检查角色、组织、患者服务关系、前置节点及证据；直接调用API不能绕过权限。来源系统+就诊事件去重，业务结果与待发送事件在同一事务保存。原型按钮不构成这些服务端实现。

最先开发真实“事件→医嘱→计划→多节点任务→反馈/异常→复诊证据”链路及权限底座；同步建立有效知识和模板审核。随后补交接排班、投诉质控及数据看板，再逐一接HIS、预约、企微、小程序，最后增加带知识引用和人工修改留痕的AI辅助。每个阶段独立形成契约、SQL、代码和测试，在codex分支通过draft PR评审，不自动合并上线。

## 原型验收与体验

运营主管进入全量扫码服务入组：选择虚构患者→模拟扫码→填写核验与服务授权→完成管家交接。进入患者全旅程服务，为该患者建立门诊或住院出院旅程，填写虚构事件编号与来源。逐节点办理，遇到医疗节点切换对应责任医生；通过快捷入口先完成报告查阅、计划批准及随访，再返回旅程关联结果。

本次自动化覆盖两条完整合成路径、事件去重、跨患者/平台管理员拒绝、实际到院前置、责任医生与计划审核、任务完成关联、未结工单阻断、无需复诊临床确认、授权撤回、旧节点提交及结案历史保护。现有回归继续通过。

这是Node VM模型/HTML标记与语法验证，没有浏览器点击或视觉验收；没有完成真实后端、企微消息、医院接口及医疗上线验收。
