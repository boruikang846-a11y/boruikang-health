# 门诊与出院全旅程后端 2.0

用户已授权接着完整旅程开发；依据 V1 需求与已认可的 V1.2 原型旅程设计实施，无额外审批步骤。

选择现有模块化单体增加旅程编排。另两种方案（新建独立服务、只给患者增加阶段字段）分别增加跨服务事务复杂度、不能区分多次就诊，因此本轮不采用。

工作顺序：
1. 先写真实 HTTP 验收：两条旅程、本人交接、到院、医嘱快照、医生审核、任务执行与查收、复诊及退出、异常闭环、权限和并发/重试。
2. 新建可增量初始化的旅程、结果、个案计划、任务关联、问题工单表；使用 MyBatis Example 和事务锁。记录结果只追加。
3. 每个端点独立 Controller/DTO，snake_case；变更携带 request_id/version。幂等返回已记录结果，同 request_id 不同内容或操作者拒绝。
4. 接入既有患者授权/报告/随访/预约，阻止暂停、退出、旧计划的任务执行。外部服务未配置不发送消息。
5. 正式管理端增加两类旅程列表、阶段详情、交接、报告核对、计划提交/审核、问题处置和结案入口。
6. 全套 Java 测试、前端测试与构建、持久化重启验收；打包新 JAR/源码/契约。保留此前导入功能。

路径：门诊 HANDOFF→CONSULT→ARRIVAL→IN_HOSPITAL→CLINICAL→PLAN→FOLLOWUP→CLOSE；出院 HANDOFF→IN_HOSPITAL→CLINICAL→DISCHARGE_HANDOFF→PLAN→FOLLOWUP→CLOSE。允许已经门诊结束/出院入口，前置阶段明确记为不适用，有核验依据，不伪造到院。

医疗判断：本次原报告由责任医生本人确认后冻结快照；个案计划节点/正文独立版本由责任医生本人批准。模板只是草稿来源；不因模板启用自动批准个案。任务从计划实例生成并关联就诊事件。计划替代取消旧版本未完成任务、历史保留。

关闭：正常复诊必须是本次报告之后的 REVISIT 已到院记录及诊疗结果，不能复用首次门诊到院或另一旅程证据；无复诊由责任医生说明依据，再由运营确认结果。未结工单/异常/随访医生待查收阻止结案。退出单独记录，不算正常完成。

本轮可验收本地真实服务闭环，不代表 HIS、企业微信或院方生产联调完成。
