# 博瑞康诊后主动干预：开发梳理 V1.1

日期：2026-10-04。依据：用户提供《患者全周期运营系统开发需求文档 V1.0》及明确要求，将诊中患者管理与诊后主动干预管理合并。本文是现有项目的开发设计，不将参考资料中的设计建议、宣传数字或待定事项视为已批准配置。

## 1. 导航与业务定位

全量扫码服务入组 → 诊前筛查 → **诊后主动干预** → 服务复盘。

原“诊中”报告、风险、计划和档案全部移入诊后主动干预；这次是管理入口合并，就诊事件仍分别记录门诊、住院、出院、体检，不将所有患者的就诊阶段改成“诊后”。咨询可在任一阶段发生。旧 `/in-care` 路由继续显示合并中心，保留 patient 和 tab 参数。

统一中心采用四组：

| 分组 | 页面 | 主要职责 |
|---|---|---|
| 服务总览 | 闭环总览 | 本人队列、患者档案、待审核、未结异常、预约待核验及下一步 |
| 资料与计划 | 报告解析汇总、风险复核、AI管理计划、长期健康档案 | 关联报告与就诊、核对原医嘱、准备并审核个体计划 |
| 服务执行 | 咨询工单、随访工作台、异常响应、邀约、预约到院、复诊跟踪 | 执行、记录反馈、临床交接和到院证据 |
| 持续服务 | 知识与宣教、服务包与方案、转诊台账 | 有效知识、获批内容、服务履约与跨机构交接 |

服务包不承担收费或开方。正式知识库、模板、交接、投诉质控和运营活动按下表补齐，不因导航合并而宣称已实现。

## 2. 本次原型交付与能力差距

| V1需求 | 本次/现有原型能力 | 正式开发补齐 |
|---|---|---|
| F01 身份、联系与授权 | 模拟扫码、核验、授权、档案关联和交接 | 患者主索引、代理关系、多用途授权、冲突核验及撤回联动 |
| F02 咨询 | 新增工单：创建→服务处理/临床反馈→已解决→确认关闭；按患者范围与负责人限制 | 优先级、截止时间、待补充、重开、转派、知识引用、发送证据 |
| F03 计划与随访 | 原报告复核、辅助草稿、医生审核、既有人工随访 | 生效模板版本、多就诊/多计划、运营执行确认、多节点实例化、取消与替代、频控 |
| F04 异常 | 既有异常列表和责任医生处理演示 | 待核验→待接单→处理中→待结果确认→关闭；备用队列、超时升级与结果证据 |
| F05 预约到院 | 既有预约、人工到院记录与复诊台账 | 将预约状态与到院状态拆开，独立证据、对账、未知状态不算未到院 |
| F06 交接 | 扫码服务的管家交接 | 交接单、接收确认、未确认保留原责任、容量及值班队列 |
| F07 质控与投诉 | 既有质量演示页 | 投诉工单、抽检、整改及复核分别留痕 |
| 知识与AI | 既有宣教草稿与审批，本地辅助计划 | 来源/版本/有效期、分库检索、医疗提交审批分离、引用与人工修改、超时人工继续 |
| 标签与内容活动 | 本次未实现 | 来源与有效期、多用途授权、人群快照、退出/频控、冻结内容版本 |
| 统计与集成 | 演示计数及医院/导入Mock | 后端口径、组织隔离、真实认证、回调幂等、事务事件、失败重试和恢复演练 |

咨询演示必须先完成核验、服务授权和管家交接；临床问题自动指定现有责任医生，护士和运营无法代填临床结果。授权撤回后阻断新建和继续处理。关闭前确认处理结果已提供，结果为空或仅通知医生不能关闭。该授权模型是原型的单一服务授权；生产需分别建模服务、推广和渠道偏好。

## 3. 最小业务闭环

1. 核验患者与代理范围，记录服务用途授权，绑定团队及负责人。
2. 关联门诊事件、出院事件或体检报告；资料不足进入待补齐。
3. 选择有效模板或人工准备计划，医疗内容由责任医生本人审核，执行安排由运营确认。
4. 发布固定版本，按步骤建立有负责人和时间窗的任务；不默认使用D3/D7或统一随访频次。
5. 执行前复核授权、医嘱版本、频控和当前责任人；记录每次实际联系与发送结果。
6. 反馈与联系尝试分别保存；消息送达不等于患者反馈或任务完成。
7. 临床问题/异常交指定团队，追踪接单、意见、患者获得处理的证据。
8. 复诊预约与实际到院分别核验，未知结果单列；完整归档到服务时间线。

## 4. 权限与状态设计

沿用现有运营主管、运营人员、护士、责任医生、平台管理员。新增岗位先映射到具体操作权限与组织范围；不让平台管理员默认访问全部患者。生产权限必须在服务端校验，页面演示不是认证。

个体医疗计划继续由患者责任医生本人审核；V1草案中的“授权临床审核人”先不扩大成任意医生。病种模板及医疗知识由科室授权审核人审批，提交人与最终审核人分离。医生自行提交医疗内容时交另一名获准审核人，不能自提自批；院方最终授权矩阵待签认。

| 对象 | 目标状态 | 必须阻断 |
|---|---|---|
| 咨询 | 新建→分派→处理中→待补充/待临床→已解决→关闭；可重开 | 临床内容由运营确认、无责任队列、无结果关闭 |
| 计划 | 草稿→待临床→待执行确认→生效→暂停/完成/撤销/替代 | 未审核执行、旧医嘱/旧版本复用审核 |
| 任务 | 待执行→待发送确认→已执行待反馈→已反馈→完成 | 发送失败算完成、无反馈伪造成功、并发重复完成 |
| 异常 | 待核验→待接单→处理中→待结果确认→关闭 | 仅已通知即关闭、超时无人承接 |
| 预约 | 建立/取消/改约 | 点击即预约、预约即到院 |
| 到院 | 待核验/已到院/确认未到院 | 接口缺失即爽约、无证据计入到院 |

## 5. 数据与接口工作包

保留现有 Java 21 / Spring Boot / MyBatis / React 工程。采用模块化业务服务；AI通过独立适配层提供草稿，不建立第二套患者业务主库。SQL、Controller、DTO及API命名按项目规范；V1里的REST路径仅为产品契约示例，具体契约另行对齐现有接口。

| 工作包 | 数据对象与关键约束 | 交付 |
|---|---|---|
| 患者与权限 | 主档、外部身份、代理关系、授权用途、团队关系、就诊事件 | 核验/撤回接口、对象级读写授权、冲突处理 |
| 咨询与工作流 | 工单、计划、任务、联系尝试、原始反馈、异常、预约及到院证据 | 状态转换接口、version与request_id、负责人、不可覆盖的状态历史 |
| 模板与知识 | 模板版本、知识版本、内容快照、审核链、适用范围与生效期 | 发布/停用、分库检索、过期阻断、历史引用不变 |
| 外部集成 | 外部事件、幂等键、事务待发送事件、失败记录与对账 | 回调鉴权、去重、有限重试、人工备用入口 |
| 质控与运营 | 投诉、整改、复核、内容执行单、标签、指标定义 | 带窗口和分母的汇总、独立导出授权、审计 |

业务表具备医院范围、版本、创建更新时间与操作者。回调按医院+来源事件+规则版本+步骤建立幂等；状态转换写入原状态、新状态、原因、操作者和请求ID。关系数据库是业务权威来源，索引可重建。保存业务和待发送事件使用同一事务；真实成功回执才能记录送达。

## 6. 开发顺序与验收

| 顺序 | 任务 | 验收依据 |
|---|---|---|
| 1 P0底座 | 患者关系、代理授权、对象权限、审计、基础工作台 | AT-01/02/03/16，跨患者/跨团队访问拒绝 |
| 2 P0服务闭环 | 咨询、模板审核基础、个体计划、任务、反馈、异常、人工预约核验 | AT-04/05/06/07/08/09/10/13，临床交接与真实结果留痕 |
| 3 知识与质控 | 知识版本/有效期、投诉整改、抽检、基础口径报表 | AT-11/20；阶段2执行前已有审核知识和模板 |
| 4 真实集成 | HIS/预约/企微/小程序按确认能力逐一接入 | AT-14/15/17/18/19，失败恢复与对账；人工方案继续可用 |
| 5 P1/P2扩展 | 有引用的AI草稿、标签、内容活动、复杂转诊与范围扩展 | AT-12及知识质量集；权限、频控、临床抽检 |

每个工作包依次输出需求、原型、数据与接口契约、代码与SQL、测试证据，版本保持一致；代码在独立codex分支开发，通过draft PR评审，不自动合并或部署。部署继续由boruikang-workflows负责。

当前缺少院方签认的服务时间、临床模板、异常接单与备用链、接口样例、实际规模，不据此虚构工期、默认医疗阈值或已接通状态。这些待定项不妨碍本轮原型合并与开发拆解。
