## 办理入口与角色

- 企业微信 `/wecom?tab=service`：运营、护士、主管按患者范围签发 / 续签、核实、撤销；医生继续承担医学审核。
- 诊后主动干预 → 患者档案 → 服务摘要与连续管理：`/after-care?step=patients&patient=<id>`。保留原档案全部页签和旧路由。
- 受邀患者 `/service#<token>`：登记、等待人工核实、查看旅程与本人 / 已核实代办患者的安排、提交反馈和查看处理结果。仅显示当前责任医生审核的有效计划及明确面向患者的回复。
- 临床工单由责任医生处理并发布回复；服务 / 投诉由运营或护士处理。发布回复不代表患者已收到，反馈核验仍走既有工单 CLOSE。

## 房颤连续管理

关系：患者主档案 → 房颤长期计划 → 多次门诊 / 出院旅程 → 既有任务与结果。首期仅 AF；目标、复盘日期、患者说明全部人工填写，责任医生审核，不内置药物、医学阈值、自动诊断或通用复诊周期。

计划有 ACTIVE / PAUSED / CLOSED 管理状态，PENDING / APPROVED / REJECTED 审核状态。更换医生或服务授权变化时，旧批准派生为 REQUIRES_REVIEW。调整内容增加修订号、保留快照并重新审核；所有写操作校验版本。责任医生做阶段复盘，记录来源旅程、评价、依据、患者说明和下一日期。历史只追加，不改写。

一个患者只能有一个未结束的房颤计划；关闭后可开启新周期。关联旅程须同院同患者。暂停 / 恢复需记录理由，结束须责任医生本人确认。旅程结案不会自动终止计划。患者授权撤回后阻断患者端和新增管理动作；新授权须重新签发、登记、核实，并重新审核长期安排，旧邀请不复活。

统一摘要显示最近 20 次旅程、10 项待办（附总数）、10 个未结问题（附总数）、10 次预约、30 次指标；指标沿用现有记录与来源，不是患者自填问卷，缺失不补零、不计算风险。计划历史显示最近 100 条并附总数。历史全量保留在数据库。各办事入口继续使用已有台账。

## 受邀服务延续

首期企微主体为博瑞康，服务江阴人民医院心血管科；企微所有者与患者医院分开。按 hospital_id 隔离，不自动向其他医院复用凭据或联系人。链接采用已配置 health.user-url，7 天有效，原文仅签发时返回；数据库只存哈希。续签撤销旧入口并重新核实，保留同一联系人、同院同患者的历史反馈，另一家属的反馈不混入。

反馈进入既有工单，患者可见处理角色、阶段、下一步和明确发布的 patient_reply；内部诊疗意见不直接公开。计划草稿、被退回内容、旧医生审核不会暴露给患者。重审后旧阶段回复不自动再次展示。

## 验收口径

一例完整案例验证流程；一批连续入组患者验证稳定性与实际结果。单例成功不代表稳定，虚构批量测试不代表真实患者结果。按 [验收与验证记录](../review/wecom-af-continuity-2.2.md) 留存证据和统计定义。

真实企微、医院事件回传和真实患者随访结果尚未验收。AI 延续病历起草与医生审核，不声称已具备医院 RAG。主管漏斗、结构化问卷、自动到院匹配及多病种模板不在本轮完成范围。
