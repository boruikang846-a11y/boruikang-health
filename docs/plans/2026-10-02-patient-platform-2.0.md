# AI 患者管理平台 2.0：系统梳理与原型范围

## 产品结构

按六个工作领域组织：工作与协作、患者与临床、服务执行、患者 H5、运营分析、质量与平台治理。现有业务、角色权限与导入流程保留。

主路径：接入与身份核实 → 建档 → 原报告与提取复核 → 风险建议复核 → 辅助管理计划 → 责任医生审批 → 任务执行与邀约 → 患者自报 / 问卷 / 问答 → 医生查收与异常处置 → 长期档案。

患者端属于用户本轮明确新增的需求，覆盖此前 HEALTH-USER 仅公开介绍的范围限制，但本轮仅新增离线演示，没有修改生产用户端 API 或认证。

## 临床与权限约束

只有责任医生本人审核计划；正文修订或原报告复核变化使审核失效。患者 H5 只显示当前版本且审核人为当前责任医生的计划。运营、护士与医生只能访问既有授权范围内患者；平台管理员不能查看患者。公开患者 H5 明确为独立虚构演示，不能作为真实认证范式。

规则评估、预测、自动建议、消息发送默认关闭。用户提供的临床阈值、用药推荐与 95% 准确率仅为待验证需求，须确定指南、适用人群、单位、终点、数据集和专家签署，不能当作已批准规则。真实风险诊断与医学处理由医生承担。

自报数据保留来源与单位，不自动覆盖医院确认数据或生成诊断。AI 原始回答不直接展示患者。扫码只进入流程，不能仅靠二维码自动认定患者身份。企业微信接入实现前按官方具体能力核实身份类型与消息权限，不把内部成员认证等同于外部患者认证。

## 开发阶段重新排序

| 优先级 | 范围 | 前置与验收 |
| --- | --- | --- |
| P0 | 权限、医院数据、患者、报告、审批、任务、审计、测试基础 | 关键路径自动化、安全阻断、真实数据库事务与幂等 |
| P0 | 企业微信身份与通知、患者授权 / 绑定 | 官方能力核实、回调验签、撤权、去重、失败处理 |
| P1 | 患者 H5、自报、问卷、医护问答、邀约与到诊 | 不越权、不展示未审核临床内容、UAT |
| P1 | OCR / NLP、辅助计划、运营分析、长期数据 | 人工复核、字段级验证、指标口径、来源追溯 |
| P2 | 规则与预测、健康评分、可穿戴、多端小程序、容量扩展 | 临床验证、模型校准、独立测试与实际负载证据 |

测试与医学安全从 P0 开始，不能到第 17 周才补齐。18 周用于分阶段试点验收，12–18 个月为完整能力与临床验证迭代周期；实际承诺需基于团队与数据准备评估。初期以单医院 100–500 例目标规划，5000+ 不作为未压测的交付声明。

## 技术与交付边界

现有 Java / Spring Boot / React 项目继续运行。本轮不建立平行 FastAPI + Express 主业务系统，不迁移数据库。下一阶段先形成技术决策：保留 Java 业务主服务、独立 Python AI 服务，或按用户指定新栈迁移；必须确定单一业务数据所有权，避免双后端重复写患者状态。

测试设计沿用 JUnit / JaCoCo + pytest HTTP 集成、Vitest、Cypress。覆盖率 >80%、适合自动化用例自动化率 >90%、提交流水线 <10 分钟为目标，需要实际报告确认。专家复核、UAT、容量测试独立记录。部署继续归 boruikang-workflows；医学与质量门槛通过前不得部署真实临床功能。
