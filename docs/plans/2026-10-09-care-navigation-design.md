# 患者诊前诊后服务导航整合

日期：2026-10-09。本文记录本轮开发目标与验收约束，不作为已完成验证或上线证明。

## 需求裁决与当前问题

用户要求以患者服务过程组织系统、展示运营人员与医护的操作步骤，减少一级菜单和重复寻找入口。原文先列出“患者池”，随后明确要求删除并入诊前，以后者为准。“患者中心”并入诊后；“运营工作台”作为全旅程的待办入口保留；删除的是独立导航入口，不删除患者档案或历史记录。

源码检查发现：

- 正式 React `App.jsx` 将工作台、患者档案、六类业务台账和管理模块平铺，难以辨认当前患者所在阶段及下一位办理人。
- React 的路由可达性原先依赖菜单列表。只删菜单会让旧台账、患者详情和医生办理入口被重定向，必须同步拆分导航归属与访问权限。
- HTML 原型已有诊前及诊后工作区，正式端已有旅程、计划、任务和问题处理，但组织方式不同；原型还保留一些超出正式实现的探索功能。
- 患者级台账与一次就诊事件的任务并非同一粒度。把入口放到一起不等于既有记录已经自动归入某次旅程，页面必须保留其实际关联范围。

## 一级菜单与二级归属

运营主管的完整一级菜单固定为以下 13 项；其他角色按既有权限显示其中可访问的部分，保持相对顺序。

| 顺序 | 一级菜单 | 主要内容 |
| --- | --- | --- |
| 1 | 患者全旅程服务 | 全流程概览、患者旅程、阶段责任与交接、运营工作台待办 |
| 2 | 企业微信 | 原有联系人、人工绑定及沟通功能 |
| 3 | 公众号 | 原有粉丝、人工绑定及沟通功能 |
| 4 | 诊前高危患者筛查中心 | 原患者池、筛查资料与导入、邀约、预约到诊、诊前问题与转诊协作 |
| 5 | 诊后主动干预 | 原患者中心及档案、资料与计划、随访咨询、异常、复诊、转诊与持续服务 |
| 6 | 宣教服务 | 原宣教内容、医学审核及发布入口 |
| 7 | 服务包与方案 | 原服务包与方案管理、履约关联 |
| 8 | 渠道管理 | 原渠道管理 |
| 9 | 统计与复盘 | 原统计、复盘与归档 |
| 10 | 医院数据 | 原医院数据及 Mock 接入状态 |
| 11 | 医护账号 | 原医护账号管理 |
| 12 | 运营设置 | 原运营配置与外部接入设置 |
| 13 | 系统介绍 | 系统范围、角色操作与能力边界 |

医生的报告、审核、结果查收和临床异常办理可归入全旅程/诊后对应环节；不得因统一菜单失去原入口或获得他人患者权限。平台管理员仍只可访问运营设置与系统介绍。

## 六类台账如何进入服务环节

| 原独立入口 | 诊前环节 | 诊后环节与衔接 |
| --- | --- | --- |
| 邀约记录 | 筛查联系、邀约就医，记录每次结果和下次安排 | 复诊或后续服务邀约，关联同一患者既有记录 |
| 随访与咨询 | 首次触达、就医流程咨询；临床问题交责任医生 | 按已审核计划执行随访、登记患者反馈、查收与再次联系 |
| 预约到诊 | 协助预约、登记预约结果、核验实际到院 | 复诊预约及到院凭据，预约成功不能代替实际到院 |
| 异常处理 | 联系失败、资料问题、待核实临床问题的登记和交接 | 临床处置、服务问题处理及患者获反馈核验 |
| 复诊跟踪 | 展示进入后续服务的衔接入口，不凭诊前名单生成复诊结论 | 依据本次报告跟踪复诊安排、实际到院与诊疗结果 |
| 转诊 | 院方承接、目标机构与转诊进度 | 后续转诊和回流结果；已发起、已承接、已到院分别记录 |

一级菜单不再出现这六类台账。工作区复用既有页面、权限及记录；同一台账可由两个阶段进入。没有可靠阶段字段时，不将全部患者记录冒充“仅诊前”或“仅诊后”数据，也不复制一套记录制造两个闭环。

## 按角色办理与交接

| 角色 | 操作步骤 | 交接结果 |
| --- | --- | --- |
| 运营人员 | 查看本人待办 → 核对来源、身份和授权 → 记录联系/邀约/预约 → 准备与原报告关联的服务草稿 → 审核通过后人工执行 → 记录反馈和后续安排 | 交接给明确的当前负责人或责任医生，保留时间、事实依据与待处理事项 |
| 护士 | 在分派患者范围内接收服务 → 核对资料 → 执行本人任务 → 记录患者反馈 → 需要医学判断时转责任医生 | 与运营人员遵循相同执行范围；护士身份不自动获得临床审核权限 |
| 责任医生 | 查看本人负责患者的原报告 → 本人确认医学依据 → 审核或退回个案意见/计划 → 查收执行结果 → 处理临床异常与必要的复诊判断 | 留存本人审核、退回或实质处置意见，由运营/护士核验患者是否已获得反馈 |
| 运营主管 | 查看团队待办与超期 → 分派负责人和责任医生 → 检查承接、未结问题及完成结果 → 复盘 | 分派不等于接收；新负责人本人确认后继续服务，主管不能代医生审核或查收 |

每个阶段说明应让工作人员知道“先核对什么、当前能做什么、完成后交给谁、下一步去哪里”。这些是现有系统的操作提示，不是尚未取得的正式医疗或运营 SOP；不新增统一医学阈值、默认治疗方案或自动联系患者规则。

临床意见只能由当前患者的责任医生本人审核后用于联系。修改正文、更换责任医生或替换计划时，应沿用已有审核失效和重新审核约束。已通知不能当作异常关闭；未完成任务、未查收结果或未闭环问题不能因导航迁移被绕过。

## 旧 URL、上下文与权限

- 保留已有 `/patients`、患者详情、`/screening`、六类台账、`/workbench` 和医生办理地址的可访问性；旧书签可直接打开对应内容，新侧栏高亮其所属工作区。
- 菜单展示、父级归属、路由授权分别处理。隐藏一级菜单不等于撤销业务访问，也不等于开放权限。
- 患者编号、任务编号、查询条件、来源工作区与返回路径按实际支持传递；从患者/旅程进入台账后，不应无提示退回全院列表。浏览器前进后退和刷新后仍须能识别当前环节。
- 复用已有患者、任务和旅程关联。尚无事件关联的旧台账只标注实际患者范围，不推断属于某次事件。
- 路由参数只是页面上下文，不能替代后端医院、角色、本人患者或任务的权限校验。

## 本轮开发边界

本轮实施导航、工作区入口、阶段操作指引、原页面嵌入及旧链接兼容；正式 React 与当前 HTML 演示的导航口径须同步，生成契约按修改后的源码更新。业务 API、状态机与数据库继续复用现有实现；若实现中确需改变业务规则或字段，应另行同步需求、契约、后端及 SQL，不能只在原型中表现为正式能力。

正式端已有旅程按门诊/出院事件关联计划、任务、问题与审计，具体持久化行为以 Java/React 代码为准。HTML 原型使用虚构内存数据；近期体检、独立个案工作区、患者 H5 等原型探索不表示正式端已交付。导航重组不表示医院、企业微信、公众号或 AI 已接通，也不表示消息已自动发送。

## 验收标准

1. 运营主管侧栏严格符合 13 项顺序；原患者池、患者中心、运营工作台和六类台账不再作为独立一级项。长标题可读，窄屏可导航。
2. 原患者导入、筛查导入、档案详情、任务办理、邀约、预约、转诊、统计及医生审核入口仍能操作；旧直链和详情返回不跳错工作区。
3. 诊前与诊后均可按环节进入相应记录；操作指引说明责任人与交接条件，患者/任务筛选不因换页丢失；共享记录不被误标为阶段专属。
4. 运营/护士不能代责任医生审核、查收或处置临床问题；医生仅可访问本人患者；主管不能代当前负责人接收；平台管理员不可访问患者业务。
5. 既有旅程审核、失败联系重试、临床异常闭环和结案约束保持有效。改菜单不能增加第二套患者档案或业务状态。
6. 执行管理端构建、导航与旧路由回归、相关原型行为检查及生成契约漂移检查；浏览器检查侧栏顺序、高亮、阶段切换、详情返回和角色入口。测试结论按实际执行结果记录，不以文档验收表代替测试。
